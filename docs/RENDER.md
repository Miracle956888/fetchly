# Launch Fetchly as a limited free beta on Render

This setup uses **one Free Docker web service** for both the React website and the API. It avoids
cross-origin cookies and manual API rewrite rules. It is simpler than a separate static site,
but the **whole site** sleeps when the web service is idle. This is a disposable beta, not
production-grade hosting or an unlimited-download service.

## Before you start

- The GitHub branch you select must already contain these changes and be **committed and pushed**.
  Render builds from GitHub, not from uncommitted files in your editor. Select that same branch in
  the Blueprint flow; otherwise Render will deploy the older code on the default branch.
- Sign up for a Render account and connect GitHub when prompted. The Blueprint creates one Free
  service and no database, Redis instance, worker, disk, or separate static site.
- The app is for media you own or have permission to save. It does not bypass authentication,
  paywalls, DRM, or platform restrictions.
- **Before inviting the public**, replace the unconfigured privacy/copyright contact in
  `client/src/pages/LegalPage.tsx` with a working contact and have the policies reviewed for your
  operation and jurisdiction. The existing text is a starting point, not legal advice.

## Deploy

1. In the Render Dashboard, choose **New → Blueprint**, connect the GitHub repository and select
   the branch containing this `render.yaml`. Leave the Blueprint path at `render.yaml`.
2. Review the proposed resources. There should be **one** `fetchly` web service, with **Docker**
   runtime and **Free** instance type. Do not add paid resources or a database for this beta.
3. Create/apply the Blueprint and wait for the build and deployment to finish. The Docker build
   installs FFmpeg, yt-dlp, the matching EJS challenge scripts, and Node 22, and builds the client
   and server. The service binds to Render's assigned `PORT`.
4. Open the service's HTTPS `https://<your-service>.onrender.com` URL. Give a cold instance about
   a minute to wake. Both the frontend and `/api/v1/*` are served from this same URL; there is no
   static-site service to create and no rewrite to configure. Do **not** set `VITE_API_ORIGIN`.
5. Open these URLs on the **same service URL**:
   - `/api/v1/health` should return `status: "ok"` and `persistence: "memory"`.
   - `/api/v1/health/engine` and `/api/v1/health/ffmpeg` should return `status: "ok"`.
   - `/admin/login` should load the admin sign-in page.
6. In the service's **Environment** tab, find `ADMIN_EMAIL` and the generated `ADMIN_PASSWORD`.
   Use them at `/admin/login`; never post either the password or `JWT_SECRET` in chat, screenshots,
   source control, or public logs. `JWT_SECRET` and `ADMIN_PASSWORD` are generated by Render for
   new variables, not stored in this repository. If a value already exists on an existing service,
   Render keeps it; verify it is strong and not a development default.
7. Try a small, public video you are allowed to save: analyze it, make an MP4, download the file,
   then repeat with an MP3. Verify playback, and test cancellation. The health checks only confirm
   that the programs exist; they **do not** prove a source platform will permit extraction.
8. Watch **Billing → Monthly Included Usage** and the service's **Metrics**. Pause or limit the
   service if usage is too high. Do not attach a payment method if you need to avoid overage bills.

If you have an older Fetchly service in the workspace, review the Blueprint plan before applying:
the `fetchly` name may create a new service rather than replacing an older `fetchly-api`. Additional
running Free services share the workspace's included instance hours and bandwidth.

## Configuration and safeguards

The Blueprint deliberately leaves `DATABASE_URL` and `REDIS_URL` unset. One process runs the API,
local FIFO queue and cleanup. Jobs, analytics, platform settings and files disappear on restart,
redeploy or spin-down. Do not add additional instances to this arrangement. Admin credentials are
seeded from the environment again each time the in-memory store starts.

| Setting | Beta value | Meaning |
| --- | --- | --- |
| `JOB_CONCURRENCY` | `1` | One active download/processing job at a time. |
| `MAX_PENDING_JOBS` | `10` | At most ten jobs waiting in the local queue; new jobs are rejected if full. |
| `MAX_CONCURRENT_ANALYSES` | `1` | One public metadata analysis at a time, in addition to the active job's re-probe. |
| `MAX_CONCURRENT_JOBS_PER_IP` | `2` | Per-IP queued or active jobs. |
| `MAX_DOWNLOAD_SIZE_MB` | `100` | 100 MiB per finished file; known source sizes are also checked early. |
| `DOWNLOAD_TIMEOUT_SECONDS` | `300` | Maximum yt-dlp download and merge time; the separate metadata probe has a 60-second timeout. |
| `PROCESS_TIMEOUT_SECONDS` | `300` | Maximum FFmpeg processing time. |
| `MIN_FREE_DISK_MB` | `256` | Reject new jobs when reported free space falls below this threshold. |
| `YTDLP_YOUTUBE_CLIENT_PROFILE` | `default` (unset) | Optional experimental YouTube-only profile; see below. |

A completed file normally expires after 30 minutes, but spin-down can erase it **sooner**. Failed,
cancelled and timed-out jobs clean their temporary directories and partial output. yt-dlp's
per-stream limit plus approximately half-second checks of the work directory and FFmpeg output are
**best effort**: fast transfers can overshoot between checks, and merging can temporarily hold
multiple copies. The final file is checked again before delivery. These controls do not enforce a
hard network-transfer or monthly bandwidth cap.

The default CORS origin uses Render's `RENDER_EXTERNAL_URL`. Same-origin requests and strict admin
cookies work without setting `CLIENT_URL`. If you use a different frontend origin later, configure
CORS and cookie behavior deliberately; do not assume this beta setup supports cross-site admin
login. If adding a custom domain while still serving everything on that one domain, use its HTTPS
URL to access the app.

## Optional YouTube compatibility experiment

**This is an unverified experiment, not a fix for a bot check.** It is off by default and is not
set in the Blueprint. Do not deploy or enable it without approving the test first. YouTube can
still require sign-in or block this server's IP; the experiment cannot clear a challenge, grant
access to restricted media, or make extraction reliable. Only test media you own or may save.

The pinned yt-dlp `2026.11.23` includes an additional `ios_producer` player client. When
`YTDLP_YOUTUBE_CLIENT_PROFILE=ios-producer` is set, the engine requests its normal default clients
**plus** that client for recognized YouTube URLs, for both metadata and stream downloads. The
[upstream client proposal](https://github.com/yt-dlp/yt-dlp/pull/17866) says it returns only
H.264/MP4A formats and does not require a PO token; the available formats or behavior can change. yt-dlp may already choose this client as a fallback in some cases,
so the experiment does not necessarily change the result. There is no extra provider, HTTP port,
account login, or user-supplied engine argument. For this profile only, yt-dlp configuration files,
third-party plugins and loading account cookies from files or a browser are disabled; yt-dlp's
bundled EJS and configured Node runtime remain available. Anonymous HTTP session cookies may still
be used internally by yt-dlp.

This is deliberately smaller than adding a third-party PO-token service: the
[provider's own documentation](https://github.com/Brainicism/bgutil-ytdlp-pot-provider) says a token
cannot overcome an IP-based sign-in restriction and may never be consulted if the player request
fails first. An extra client may issue several additional upstream requests, increasing latency and
bandwidth or triggering source rate limits. The existing 60-second metadata deadline, download
timeout, queue and admission limits remain; they are not a hard bandwidth cap. One public analysis
and one job's separate re-probe can still run simultaneously on the beta service. Free-tier CPU and
memory constraints remain relevant. The experiment has not been verified against Render or a real
YouTube download.

After an operator explicitly approves a test, prefer a disposable test service and use the same
small public video you are allowed to save for both runs:

1. Confirm the candidate image uses `yt-dlp` `2026.11.23`; leave the setting unset for the baseline.
   Record whether analysis succeeds, which formats are offered and how long it takes. A green
   engine health check is **not** an analysis or download test.
2. Set `YTDLP_YOUTUBE_CLIENT_PROFILE=ios-producer` in that test service's Environment and let
   Render apply/redeploy the configuration. Its startup log records `youtubeClientProfile` as a
   configuration value, not proof YouTube accepted it. If running a separate worker, configure the
   same profile there. Changing environment values or redeploying can discard the beta's in-memory
   jobs and files; a new service or deploy can also use a different outbound IP.
3. Analyze the same video again. If formats appear, actually download and play a small MP4 and an
   MP3, and watch Render's time, memory, CPU and bandwidth metrics. Analysis alone is not evidence
   that stream downloads work. Avoid repeated rapid retries. Compare both runs and record any
   sanitized error category without sharing source URLs, account data, cookies or other secrets.
4. Remove the setting or change it to `default` and apply the change to roll back. If YouTube still
   asks for sign-in, stop the experiment: the server cannot complete that verification. For your
   own uploads, YouTube Studio or Google Takeout may offer an owner download instead.

Use only the documented `default` or `ios-producer` values; invalid values stop startup. Do not
supply credentials or cookies. With yt-dlp `2026.11.23` and Node 22+ installed locally,
`python scripts/check-youtube-profile.py` checks the client selection and account-config isolation
**offline**; it does not test a source or the Render network. Upgrading yt-dlp requires rechecking
the profile and repeating the real-source test. Render preview services may inherit production
environment variables; do not use production data for an isolated test.

## Free-tier limits and risk

As of November 2026, Render Free web services have 512 MB RAM and 0.1 CPU, sleep after 15 minutes
without inbound traffic, and can take about a minute to wake. Render may restart or suspend a Free
service, and its ephemeral filesystem is lost on sleep/restart/redeploy. A Hobby workspace shares
750 Free instance-hours, 5 GB outbound bandwidth and 500 build minutes per month across its
services. Check the current [free-tier limits](https://render.com/docs/free),
[pricing](https://render.com/pricing/) and [build-pipeline limits](https://render.com/docs/build-pipeline)
in case they change.

At most roughly 50 deliveries of 100 MB each would consume 5 GB **before** pages, API traffic,
retries and other services. Without a payment method, exhausting outbound bandwidth suspends Free
services for the rest of the month; with one, overage may be billed. Running out of build minutes
can stop new builds. Render may also suspend a Free service for unusually high service-initiated
traffic. This app does not have a monthly quota, so a small number of users or abusive traffic can
exhaust the allowance quickly.

Cloud IPs may be blocked or rate-limited by YouTube, TikTok, Instagram and other sources, and
extractors can break as platforms change. `yt-dlp` is pinned in both Dockerfiles for reproducible
builds; update that pin and redeploy when needed. Do not rely on a green health check as proof of
platform support.

Initial URL validation is **not complete network isolation**: extractors can make additional
requests or follow redirects. Do not attach sensitive private-network services to this disposable
beta. Before wider public traffic, add robust egress/SSRF controls, stronger abuse and bandwidth
controls, persistent storage, monitoring and a deployment designed for the expected load.

The old placeholder canonical URLs, nonexistent social image and placeholder sitemap were removed.
Once you settle on a real domain, add correct per-page canonical metadata, a real social image and
a sitemap for that domain. Render may serve a disallow-all `robots.txt` while a Free service sleeps.

## Troubleshooting

- **The website/API is missing or shows old behavior:** check that the Blueprint deployed the
  intended pushed branch and completed successfully. Inspect the service's build and runtime logs.
- **Service won't start because of secrets:** production rejects the development JWT secret and
  default/short admin password. Set strong unique values in Render's Environment tab and redeploy.
- **Admin login fails:** use the exact generated email/password over the same HTTPS service URL.
  Editing the values restarts the in-memory beta and invalidates current jobs/sessions.
- **Engine/FFmpeg health is unavailable:** check the Docker build logs. A successful health check
  still cannot guarantee that a platform or a particular video is downloadable.
- **Source unavailable, sign-in request, bot check, timeout, or incomplete download:** retry a small
  permitted public file and inspect `yt-dlp exited non-zero` or `yt-dlp download failed` in the Render
  logs. A public video can still trigger a source sign-in or bot challenge from a cloud IP; the app
  cannot clear that challenge. Update the pinned yt-dlp/EJS versions when appropriate, but do not
  assume an update will resolve a platform block. Remove private URLs and secrets before sharing
  diagnostic logs; never share passwords or browser cookies.
- **Checking an engine update:** deploy the Git commit that updates the Dockerfile, then compare
  `/api/v1/health/engine` with the `yt-dlp[default]` version pinned in that commit. A **restart**
  reuses the existing image and does not install a new version. A Render dashboard deploy of a
  specific commit disables automatic deploys; check that setting afterward. This beta stores jobs
  and files in memory/on temporary disk, so they can be lost during a redeploy. Once the expected
  version is live, test a small permitted video; a green health check only means the engine starts.
- **Storage full or queue full:** wait for work to finish or files to expire, use smaller media,
  and inspect the service's resource metrics. The `MIN_FREE_DISK_MB` threshold is a safeguard, not
  a guarantee of available disk space.
